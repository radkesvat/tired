# Packaging and installation

Release preparation is local. The maintainer publishes the repository and GitHub
assets, signs source uploads if desired, and handles any PPA, Debian or Snap Store
submission. No hosted APT repository, archive acceptance or store listing is implied
by a locally produced package.

## Direct archives

The release assets are `tired-0.1.0-linux-amd64.tar.gz` and
`tired-0.1.0-linux-arm64.tar.gz`, with `SHA256SUMS`. Use the artifact matching the
host architecture and glibc 2.35+ baseline. The complete payload contains both
executables, profiles, schemas, defaults, documentation and platform metadata.

After downloading the installer and release assets from the maintainer's published
location, inspect the script and run:

```sh
sh install.sh --version 0.1.0
sh install.sh --version 0.1.0 --prefix /opt/tired
sh install.sh --prefix /usr/local --uninstall
```

The default prefix is `/usr/local`. The private installation manifest identifies
owned payload and refuses unrelated files, unsafe ancestry, changed payload and
symlinks/hardlinks. Downloads and complete staging precede replacements. Reinstall
or select a newer explicit version to upgrade. An obsolete owned payload file is
removed only after checking the old manifest. Services and state are never changed.

For manual review, verify the selected archive with its `SHA256SUMS` entry, extract
it into a temporary directory and inspect `usr/local` under the archive root before
copying that complete tree into an administrator-owned prefix. Prefer the installer
for recorded ownership and uninstall. A user-owned prefix cannot be trusted by the
root helper; user scope is available under that account's own authority.

## Debian binary and source packages

Distribution builds use `/usr` and installed **shared** development/runtime
libraries. Build dependencies are declared in `debian/control`; shared runtime
dependencies are generated by `dh_shlibdeps`. There are no package scripts that
stop/delete generated services or install permissive authorization policy.

```sh
sudo apt install ./tired_0.1.0-1_amd64.deb
sudo apt install --reinstall ./tired_0.1.0-1_amd64.deb
sudo apt remove tired
sudo apt purge tired
```

Use the `arm64` filename on ARM64. Package removal/purge removes package payload,
not runtime-created units, private environments, app data or control-plane state.
Those files are not package conffiles and remain available to systemd. Reinstall
tired to manage them again, or use standard systemd commands.

A rebuildable source delivery includes the `.dsc`, upstream `.orig.tar.gz`, Debian
changes archive, `.changes` and `.buildinfo`; a binary `.deb` alone is insufficient.
The unsigned local build is:

```sh
tar -xf tired_0.1.0.orig.tar.gz
cd tired-0.1.0
sudo apt-get build-dep .
dpkg-buildpackage -us -uc -sa
lintian --pedantic ../tired_0.1.0-1_amd64.changes
```

Build in a clean Debian environment on each architecture. The packaging requests
Clang/LLD Release LTO, distro hardening/reproducibility flags and DWARF4 debug data
compatible with the baseline `dwz`; separate debug-symbol packages are produced.
Do not change linkage/compiler policy silently to make a package build.

The maintainer can inspect `.changes`, sign with their own key, and seek Debian
review/sponsorship under the [official maintainer workflow](https://www.debian.org/doc/manuals/maint-guide/build.en.html).
An initial local package has no Debian intention-to-package issue to close;
`initial-upload-closes-no-bugs` remains an expected Lintian finding until the
maintainer opens and supplies that issue. No issue number or submission is invented.

## Ubuntu PPA preparation

A PPA accepts signed source uploads and builds its own binaries. Select the actual
maintainer-owned PPA and target series. Create a series-specific changelog revision,
for example `0.1.0-1~jammy1` or `0.1.0-1~noble1`, verify build dependencies in that
series, run a clean source build, then sign/upload only with the maintainer's chosen
key and authorization. Keep those variants separate from the Debian unstable
changelog. No PPA destination or credentials are supplied by the project.

The local preparation recipe produces separate unsigned `.dsc`, changes archive,
source `.changes` and `.buildinfo` sets using the same upstream archive:

```sh
cmake -DUPSTREAM_SOURCE_ARCHIVE="$PWD/build/release/0.1.0/tired-0.1.0.tar.gz" \
  -DOUTPUT_DIRECTORY="$PWD/build/ppa-source" -DVERSION=0.1.0 \
  -P cmake/UbuntuSourcePackages.cmake
```

Choose a fresh output directory. This source-only preparation does not claim a
Launchpad build or acceptance. Rebuild and check the selected series' actual build
dependencies in its clean environment before the maintainer signs any upload.

## Snap preparation

`snap/snapcraft.yaml` describes the complete classic-confinement package from the
direct static-dependency build, with a compatible core22 base and dynamic glibc.
It is a command-line tool, not a daemon. Host units/state and captured app paths must
remain outside snap-owned revision storage. Snap refresh/removal must not invalidate
those services. The helper remains an ordinary authorized root executable.

Classic confinement needs external review. The
[confinement assessment](snap-classic.md) describes exact host access,
strict-interface limitations, validation and maintainer review materials. Local
`--dangerous --classic` installation of a prepared package in a disposable VM is
qualification, not store eligibility or approval. No development-confinement
fallback is presented as production functionality.

## Release contents and validation

Before publishing a version, review the source, tests, licenses and qualification
report. Verify both architecture builds and their checksums, helper/data payload,
dependency metadata and relinking materials. Publish the reviewed source and
matching version tag, then verify the README installer and manual-download links
against the published release assets.

Keep native direct archives, Debian binaries/source artifacts, Snap artifacts,
checksums, dependency/license notices, static relinking objects and corresponding
sources together. Direct releases keep third-party libraries static while glibc
stays dynamic. Distribution packages keep those libraries distro-managed. Include
build versions and ELF metadata; never call this fully static portability.

The release workflow runs only on an explicitly authorized version tag. Publication
permissions are confined to its final release job. Local build artifacts remain
under `build/`; signing/upload credentials are never embedded in the repository.
Consult [compatibility](compatibility.md), [dependencies](dependencies.md) and
[release qualification](release-validation.md) for actual evidence and limitations.
